## 规则与状态所有者（移植裁定）

1. **凭据数据根**：Host 只向 Main 传 `targetBaseDir`；Main 独占系统密钥并推导凭据路径——上游 `上游官方根字面量 join 调用（desktopHostProcess:356）`（desktopHostProcess.ts:356）**必须改为 OPENZWORK_DATA_DIR_NAME**（唯一产品数据根规则，同 main/index.ts:524 先例）。失败中止新路径保存；用户级根统一 `.openzwork`。

   **启动门禁的源/目标裁定（2026-11-15 返工修正，独立复核 F1/G1）**：上游运行时通道里 Main 的 cipher 天然绑定「当前根=源」，向 Host 传入的目标共享语义自洽；我方把复制搬到启动门禁后，Main 的运行时根在 `applyEarlyDataBaseDirBootstrap` 已指向目标，**不能**从运行时根推导源。源必须来自迁移计划（唯一所有者 `pendingDataBaseDirMigration`）；**目标必须来自复制执行计划的 canonical 结果 `dirname(plan.targetRoot)`**——它与 ③ 提交的 `dataBaseDir`、未来 Host 绑定的是同一路径。计划 `targetBaseDir` 只是用户输入的 resolve 结果，可保留符号链接别名，不能当密钥条目名（G1 缺陷：系统条目按 `resolve(凭据路径)` 分条目，登记到别名条目而重启按 canonical 找不到，复制过去的密文 `CREDENTIAL_SECURE_STORAGE_UNAVAILABLE`）。源端继续使用计划 `sourceBaseDir`（既有密钥 owner 实际使用的命名，不做 realpath）。两端凭据路径均以 OPENZWORK_DATA_DIR_NAME 常量构造。所有者与事件顺序：

   ```text
   pendingDataBaseDirMigration（所有者：settings 文件，settingService 读写）
     │ applyPendingDataBaseDirMigration（启动门禁，业务 Host 启动前）
     ├─① copyDataDirectory(source→target)          [owner: services paths]
     │      产出执行计划 plan.targetRoot（realpath canonical，别名已归一）
     ├─② shareCredentialKeyWithDataRoot({source: plan.sourceBaseDir,
     │                                     target: dirname(plan.targetRoot)})
     │      Main 装配：cipher 绑定 join(source,.openzwork,v2,credentials.json)
     │      → shareKeyWithCopiedCredentials(join(target,…))   [owner: Main 独占系统密钥]
     │      目标已有不同密钥 → 拒绝覆盖抛错；同路径短路保留
     ├─③ writeSettingsAt(dataBaseDir = dirname(plan.targetRoot))  [与②同一目标，仅②成功后执行]
     └─②失败 → 抛出中止：指针不变、计划保留（下次启动重试）；取消则解封源根
   ```

2. **Linux 文件密钥回退**：仅 Desktop Main 首次访问前显式启用且目录未绑定来源；0600 排他发布；不覆盖已有来源/密文；Host/内置 CLI 跟随 Main；独立 CLI/Server、macOS/Windows 不扩大启用；不引入任意 fallback。
