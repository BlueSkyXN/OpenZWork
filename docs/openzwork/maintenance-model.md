# OpenZWork 维护模型

OpenZWork 持续合入上游 ZCode，同时保留自己的功能、行为调整和裁剪。维护工作由 AI Agent 执行。本文规定文件放在哪里、改动记在哪里、怎样识别一个文件或功能的来源，以及维护经验怎样沉淀。执行方法见 `.agents/skills/openzwork-maintenance/`。

## 目标与检查

维护方法服务三件事，每件事有一项可以运行的检查：

| 目标   | 含义                                                 | 检查                                                                         |
| ------ | ---------------------------------------------------- | ---------------------------------------------------------------------------- |
| 跟得上 | 上游每个版本的新增与修复都有取舍，并尽快合入         | 每个已合入的上游版本有上游变更清单与同步记录，见「合入上游的记录」           |
| 守得住 | OpenZWork 的功能、行为调整和裁剪在合入上游后仍然成立 | 每个 `active` 台账条目至少有一项在核心 CI 中运行的保证，见「保证」           |
| 分得开 | OpenZWork 代码与上游代码的交叉面尽量小               | `pnpm openzwork:scan --entries` 给出每个条目的接线面，合入上游前后各记录一次 |

修复上游缺陷（`OW-P`）、改变上游行为（`OZ-C`）、新增功能（`OZ-F`）和裁剪（`OZ-D`）都是需要守住的定制，按同一套检查处理。

## 双轨

| 轨道   | 内容                                           | 维护方式                                                   |
| ------ | ---------------------------------------------- | ---------------------------------------------------------- |
| 上游轨 | 上游已有的文件：代码、文档、技能、配置         | 尽量保持上游原文。合入上游新版本时，这些文件直接随上游更新 |
| 下游轨 | OpenZWork 新增的文件，以及对上游文件的必要改动 | 新增内容放在可识别的位置；改动上游文件时登记到台账并加标记 |

合入上游新版本时，Agent 按技能中的同步流程处理两轨的交叉点，也借此吸收上游的新做法。

## 来源分类

基准是 `docs/openzwork/ledger.yaml` 记录的上游提交（最近一次合入的上游快照）。扫描工具按下表给每个路径分类：

| 分类                | 判定                                   | 要求                                                      |
| ------------------- | -------------------------------------- | --------------------------------------------------------- |
| `upstream`          | 内容与上游基准一致                     | 保持原样                                                  |
| `upstream-format`   | 与上游的差异只来自格式化               | 不允许存在；恢复为上游原文                                |
| `upstream-identity` | 差异只有用户级数据根 `.openzwork` 改名 | 允许；只改必要的行                                        |
| `upstream-modified` | 我方实质修改的上游文件                 | 只允许代码文件；接线处加标记。文档改为另存 OpenZWork 版本 |
| `removed`           | 上游有、我方已删除                     | 裁剪域由 `drop` 条目的 glob 覆盖                          |
| `openzwork`         | 上游任何版本都没有的文件               | 应由台账条目认领，或属于 OpenZWork 维护文档与工具         |
| `retained`          | 上游已删除、我方保留                   | 应由台账中的 `retain` 条目认领                            |
| `moved`             | 内容与某个上游文件一致，但路径不同     | 说明移动原因                                              |

认领指台账条目、下游补丁或文档版本登记覆盖了某个路径，用来在合入上游时从文件找到受影响的定制。需要认领的是：OpenZWork 新增的文件、定制接线或依赖的上游文件（写入条目的 `hooks`）、裁剪域和保留文件。其余 `upstream-modified` 文件不要求逐个认领；扫描汇总给出它们的数量和增删行数，用来观察交叉面的变化。

识别"上游原作者写的"和"OpenZWork 写的"以 Git 历史中的上游快照为准。上游快照提交位于本仓库历史中（每次合入使用双亲 merge），本机镜像仓用于获取上游的新版本。

## 文档布局

| 内容                            | 位置                                                                                                                                                                                        |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 上游原有文档                    | 原路径，保持上游原文，不做任何修改                                                                                                                                                          |
| 上游文档的 OpenZWork 版本       | 只在代码读取、规则引用或 OpenZWork 改写维护时保留：同目录，文件名加 `-openzwork`；登记在 `docs/openzwork/upstream-doc-variants.yaml`。其余差异见 `docs/openzwork/README.md`「与上游的差异」 |
| OpenZWork 产品 spec             | `docs/specs/<名称>-openzwork.md`，与上游的 `docs/specs/` 同目录                                                                                                                             |
| OpenZWork 测试计划              | `docs/testing/<名称>-openzwork.md`                                                                                                                                                          |
| 上游其他目录下的 OpenZWork 文档 | 同目录，文件名加 `-openzwork` 后缀                                                                                                                                                          |
| 维护文档                        | `docs/openzwork/`：`upstream/` 上游整合与验证记录，`patches/` 下游补丁，`release/` 发行，`ci/` CI 与测试基础设施，`records/` 历史验收记录                                                   |

`docs/openzwork/README.md` 是全部 OpenZWork 文档的索引。

## 上游文档与 OpenZWork 的差异

判断一份上游文档要不要 OpenZWork 版本，只看一个问题：OpenZWork 是否需要自己维护这份文档的内容。

| 情况                                                | 处理                                                        | role         |
| --------------------------------------------------- | ----------------------------------------------------------- | ------------ |
| 代码读取该文档（审计脚本、晋级脚本、开发站点等）    | 同目录保留 `<名称>-openzwork<扩展名>`，读取方改为读取该版本 | `tool`       |
| OpenZWork 的规则或 spec 以该文档为准                | 保留 OpenZWork 版本，引用方链接到该版本                     | `rule`       |
| OpenZWork 改写并持续维护（描述 OpenZWork 当前行为） | 保留 OpenZWork 版本                                         | `maintained` |
| 其他                                                | 只保留上游原文，不建副本                                    | —            |

- 上游文档原文不动，包括格式。
- 不建副本的上游文档，OpenZWork 与它的差异（移除的功能、改变的行为、用户级根）统一写在 `docs/openzwork/README.md` 的「与上游的差异」。该表与台账一致，由门禁校验；读上游文档时按该表理解。
- 新的 OpenZWork 内容写进 OpenZWork 自己的文档（`docs/specs/*-openzwork.md`、`docs/openzwork/`），不为补几句话复制整份上游文档。
- 保留的 OpenZWork 版本登记在 `docs/openzwork/upstream-doc-variants.yaml`：`role`、`usedBy`（`tool`、`rule` 必填）、`kind`、`upstreamBlob`。合入上游后原文变化，`--check` 按 `upstreamBlob` 提示复核。`pending` 表示少量 OpenZWork 内容待用户确认去留。
- `tool`、`rule` 的 `usedBy` 由门禁验证实际读取目标，不是文件名出现即可：OpenZWork 版本存在时，读取方必须选中该版本。允许三种写法：
  - 直接写 OpenZWork 版本路径（如 `resolve(__dirname, "…/zcode-feature-graph-openzwork.yaml")`）；
  - 把原文路径传给登记的选择函数——`openzworkDoc(原路径)`：版本存在时返回版本、不存在时回退原文。选择函数按名字登记（当前只有 `openzworkDoc`），其定义处带 `OpenZWork(OZ-F001)` 标记；
  - `rule` 文档用 Markdown 链接指向 OpenZWork 版本。

  直接读取原文路径（登记了版本却仍读上游），或文件名只出现在注释与无关字符串里，都判失败；关系失效时删除 OpenZWork 版本或调整 `role`。

- 与上游原文逐字节一致的上游文档描述的是上游产品，净化门禁 WP-03、WP-08、WP-09 的文本扫描跳过它们；OpenZWork 版本照常扫描。
- OpenZWork 自有文档链接到有 OpenZWork 版本的上游文档时，链接该版本；上游原文的内容和锚点与它不同。OpenZWork 版本没有对应内容、需要引用上游原文时，链接文字以「上游」开头，例如 `[上游远控架构：后台恢复](…)`。
- 代码文件按「代码」一节原地修改；上游技能中的脚本按「技能布局」处理。

## 技能布局

`.agents/skills/` 下来自上游的技能整体保持原作者的文件，包括其中的脚本。需要 OpenZWork 的差异时用新增文件承接：

| 需要的差异                                     | 做法                                                                                                                                                       |
| ---------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 说明上的差异（OpenZWork 没有某功能、路径不同） | 技能不动；差异写在 `docs/openzwork/README.md`「与上游的差异」或根 `AGENTS.md`                                                                              |
| 不同的内容（数据、图谱、清单、模板）           | 同目录新增 `<名称>-openzwork<扩展名>` 并登记到 `upstream-doc-variants.yaml`，读取方改读该版本                                                              |
| 不同的流程（要改 `SKILL.md`）                  | 写成 `openzwork-maintenance` 的子能力，或新建 OpenZWork 技能并在开头指明先读哪个上游技能。技能加载只认 `SKILL.md`，不建 `SKILL-openzwork.md`               |
| 不同的行为（要改脚本）                         | 只允许用户级根改名这一种原地改动：只改那一行，不加注释，扫描把该文件归为 `upstream-identity`。其余情况复制为 `<名称>-openzwork<扩展名>` 并登记，原脚本不动 |
| 整个技能不适用                                 | 保留不用并在「与上游的差异」注明，或整个删除并登记 `drop` 条目；不删改其中部分文件                                                                         |

上游技能目录下可以新增 OpenZWork 文件。上游更新技能时，原文件随合并更新；登记过的 OpenZWork 版本由 `upstreamBlob` 提示复核。

OpenZWork 专用的维护方法、扫描用法和经验集中在 `.agents/skills/openzwork-maintenance/`：入口 `SKILL.md` 只做路由，子能力位于 `references/<名称>/GUIDE.md`，经验库位于 `knowledge/`。

## 代码

- 新功能代码优先放在新文件或新模块中；上游文件只保留接线所需的改动。
- 上游文件里的接线处加注释 `OpenZWork(<台账编号>): <原因>`；缺陷修复继续使用 `OW-Pxxx`（见 [下游补丁清单](patches/downstream-patch-registry.md)）。存量的其他写法在下次修改该处时统一。
- 功能依赖的上游共享组件、store、协议和函数登记在台账条目的 `hooks` 中。同步时，扫描工具会报告上游对这些文件的改动。
- 上游文件不做格式化、注释润色或与任务无关的重构。改动上游文件时夹带的格式化同样不允许：与上游的差异只包含实质改动。已经被整文件格式化的上游文件用 `.agents/skills/openzwork-maintenance/scripts/unformat.mjs` 恢复，方法见技能的 `code-boundary` 子能力。
- 恢复工具以已提交的内容生成方案。`--apply` 写入前检查全部目标文件；目标有暂存或未暂存的改动，或生成方案后 HEAD 已变化时，整次拒绝写入。`--verify` 要求对比提交和上游基准有效，Git 读取失败时返回非零。
- `pnpm fmt` 和 `pnpm fmt:check` 只处理 OpenZWork 自己的文件，由维护工具先按上游历史筛选，再交给 oxfmt。上游原文、改名、实质修改、保留和移动文件均跳过；新建且未被 Git 忽略的自有文件也参与。可以传文件、目录或 glob 缩小范围，`--list` 预览候选清单。候选为空时不启动 oxfmt；明确指定上游文件时拒绝执行。CI 执行同一范围的 `fmt:check`。

## 台账

`docs/openzwork/ledger.yaml` 记录每个 OpenZWork 功能、行为调整、裁剪和保留：

| 字段               | 含义                                                                                                       |
| ------------------ | ---------------------------------------------------------------------------------------------------------- |
| `id`               | `OZ-F`（新增功能）、`OZ-C`（改变上游行为）、`OZ-D`（裁剪上游功能）、`OZ-R`（上游已删、我方保留）加三位数字 |
| `kind`             | `feature`、`change`、`drop`、`retain`                                                                      |
| `status`           | `active`、`undecided`（需要用户决定）、`retired`（已退役，保留记录）                                       |
| `title`、`summary` | 名称与一句话说明                                                                                           |
| `spec`             | 对应的 spec 或记录，可写多份                                                                               |
| `paths`            | 认领的路径或 glob。`drop` 条目的路径必须不存在，其余条目的路径必须存在                                     |
| `hooks`            | 可选，功能依赖或接线的上游文件                                                                             |
| `gates`            | 可选，`drop` 条目对应的净化门禁断言名称片段。路径不存在由台账检查保证，文本残留由这些门禁保证              |
| `tests`            | 可选，回归测试路径                                                                                         |
| `unguarded`        | 条目暂时没有保证时必填：原因与补齐方式。已有保证的条目不能保留该字段                                       |
| `source`           | 决定的来源：PR、提交或 spec 段落                                                                           |

新增功能、改变上游行为或裁剪上游功能，都要在同一个 PR 中更新台账。

### 保证

每个 `active` 条目至少有一项在核心 CI（`.github/workflows/ci.yml`）中运行的保证：

| kind                          | 保证                                                                                                                         |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `feature`、`change`、`retain` | `tests` 或 `paths` 中至少一个测试文件在核心 CI 中运行：列入 `tests/ci/core-tests.json`，或由 `ci.yml` 的步骤点名（含通配符） |
| `drop`                        | 门禁检查 `paths` 不存在；文本残留另由 `gates` 保证                                                                           |

- 没有保证的条目填写 `unguarded`。新增条目应带着保证合入，`unguarded` 只用于登记存量或确实无法在 CI 中运行的情况。
- Extended（不阻塞合并）、桌面 E2E 和待人审用例不计入保证。
- `ci.yml` 步骤点名的测试文件必须存在。上游删除测试后，Vitest 会忽略匹配不到文件的过滤器，步骤仍然通过，保证却已经消失。
- `pnpm openzwork:scan --entries` 列出每个条目的保证与接线面。

## 合入上游的记录

每个合入的上游版本在 `docs/openzwork/upstream/` 留下记录：

- `v<版本>-integration.md`，合并前写。其中的上游变更清单按功能域列出上游这一版的新增与修复，每项写明处置（吸收、裁剪、暂缓）和理由；暂缓项写明重新评估的条件。
- `v<版本>-validation.md`，合并后写。其中的同步记录包括：上游发布日期与合入 main 的日期；`--upstream` 预演的吸收概览与冲突数；我方已删文件中移植了哪些上游修复；受影响台账条目的复核结论；合并前后 `--entries` 的接线面；合并后发现的回归及其补丁或 PR。

门禁检查台账上游版本对应的 `v<版本>-integration.md` 存在。写法见技能的 `upstream-sync` 子能力。

## 扫描

`pnpm openzwork:scan` 运行 `.agents/skills/openzwork-maintenance/scripts/scan.mjs`：

- 默认输出全仓来源分类与台账认领情况，以及 `upstream-modified` 文件相对上游基准的增删行数。
- `--path <路径…>` 输出单个路径的来源、首次出现的上游版本、当前分类和认领条目。
- `--entries` 输出每个台账条目的保证（核心 CI 中运行的测试、净化门禁或 `unguarded`）与接线面（`hooks` 中被我方修改的上游文件数及增删行数）。
- `--upstream <提交或 tag>` 预演合入新上游：先给出吸收概览（上游改动的文件中，我方未改动可直接吸收的、我方改过需要合并的、我方已删需要阅读的、上游新增的各有多少），再列出冲突文件、冲突中涉及台账条目的文件、上游新增文件中命中 `drop` 路径的文件、上游修改的我方已删文件。
- `--check` 执行门禁检查，由 `tests/ci/openzwork-maintenance.test.mjs` 在 CI 中调用。

## 经验库

`knowledge/` 下按类型分为三份 YAML：`pitfalls.yaml`（踩坑）、`diff.yaml`（diff 与识别经验）、`decisions.yaml`（取舍先例）。经验库由 Agent 在任务中更新，规则如下：

- 只记录经过实际任务验证的经验，并附上可核对的证据：提交、PR、文件路径或 spec 段落。推测和一次性的过程信息不记录。
- 新增前先在三份文件中搜索；已有相近条目时更新原条目。
- 一条经验只写一个可执行的做法，写明适用场景。
- 发现条目错误或过时，将 `status` 改为 `superseded` 并填写 `supersededBy`，或在没有替代时直接删除。
- 每份文件的 `active` 条目不超过 40 条，超过时先合并同类条目。
- 字段、编号格式和数量上限由 CI 校验。

## 规则的存放与使用

每条规则只在一处写全，其他位置引用它：

| 位置                                                                   | 放什么                                         | 什么时候读                               |
| ---------------------------------------------------------------------- | ---------------------------------------------- | ---------------------------------------- |
| 根 `AGENTS.md`「上游与 OpenZWork 维护」                                | 每次改动都会用到的规则，一条一句；其余指向本文 | 开始任何任务时                           |
| 本文                                                                   | 全部规则、判定标准和检查方式                   | 做维护类任务，或对规则的含义有疑问时     |
| 技能 `references/<子能力>/GUIDE.md`                                    | 执行步骤和命令                                 | 执行对应子能力时                         |
| 技能 `knowledge/`                                                      | 经过验证的经验与取舍先例，附证据               | 开始维护任务前，合入上游前               |
| `scan.mjs --check` 与 `tests/ci/`                                      | 能自动判定的规则                               | 每个 PR 的 CI                            |
| `ledger.yaml`、`upstream-doc-variants.yaml`、`downstream-patches.yaml` | 每项定制、文档版本和补丁的事实                 | 扫描工具与门禁读取，Agent 查询来源时读取 |

新增或修改一条规则，按这个顺序做：

1. 先改本文：写明规则、判定标准，并在下表登记检查方式。
2. 再改用到它的指南，写出执行步骤。
3. 能自动判定的，补门禁和回归用例（`scripts/test/openzwork-maintenance-scan.test.mjs`）。
4. 只有每次改动都会用到的规则才在根 `AGENTS.md` 加一句。
5. 规则来自一次具体事故时，把事故写成经验条目，在指南中引用编号。

### 规则与检查

「检查」一列写明规则由什么保证。标为「靠执行」的规则没有门禁，Agent 按指南自查，审查时重点看。

| 规则                                               | 详细位置                                             | 检查                                                                                                                           |
| -------------------------------------------------- | ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 上游文档保持原文，差异另存 `-openzwork` 版本并登记 | 「文档布局」「上游文档与 OpenZWork 的差异」          | 门禁 4、7                                                                                                                      |
| 上游技能保持原作者的文件                           | 「技能布局」                                         | 门禁 4、11                                                                                                                     |
| 上游代码只改行为必需的行，不格式化                 | 「代码」                                             | 门禁 6：纯格式化、改名加格式化一律拦截；夹带实质改动时，格式化造成的差异达到 20 行且超过实质改动的一半即拦截。低于门槛的靠执行 |
| 新功能放新文件，上游文件只留接线并加标记           | 「代码」                                             | 靠执行；`--entries` 的接线面用于审查                                                                                           |

## 门禁

`tests/ci/openzwork-maintenance.test.mjs` 校验：

1. 台账、经验库与 `upstream-doc-variants.yaml` 的字段、编号和取值。
2. 台账上游基准是 HEAD 的祖先，并与根 `package.json` 版本的前三段一致。
3. `drop` 条目的路径不存在；其他 `active` 条目的路径存在。
4. 上游文档与技能（md、yaml、json 等文档类文件）与上游原文逐字节一致；同目录的 `-openzwork` 版本都已登记并写明 `role`，`tool`、`rule` 的引用关系仍然存在；登记时记录的 `upstreamBlob` 与当前基准一致，不一致说明上游更新了原文，需要复核 OpenZWork 版本。
5. 台账中每个 active、undecided 条目都出现在 README 的「与上游的差异」中。
6. 任何上游文件都不能只有格式化差异；夹带实质改动的上游文件，格式化造成的差异不能达到 20 行且超过实质改动的一半。格式化造成的差异按「与上游原文的差异行数，减去双方都格式化之后的差异行数」计算，`.oxfmtrc.json` 忽略的文件不检查。
7. OpenZWork 自有的 Markdown 中，指向已登记上游文档的相对链接都改指其 OpenZWork 版本；链接文字以「上游」开头的除外。
8. 每个 `active` 条目有核心 CI 中的保证，或写明 `unguarded`；已有保证的条目没有残留的 `unguarded`。
9. `ci.yml` 步骤点名的测试文件都存在。
10. 台账上游版本对应的整合文档存在。
11. 上游技能的原有文件与上游一致，脚本最多只差用户级根改名；其中被删除的文件由 `drop` 条目认领。
